# 跟进参考上游项目仓库

把用户指定的参考上游项目仓库搬进**当前仓库**，并让它在之后每天自动更新、自动合并 ——
**一次配置，之后全程无人值守**。

落地极简：目标仓库只多 **2 个文件**

| 文件 | 作用 |
| --- | --- |
| `.cnb/sync-upstream.sh` | 同步脚本（原样复制，**不要重写**） |
| `.cnb/git-sync.yml` | 定时同步 + 开 PR + 自动合并的流水线（原样复制，只填占位符） |

再加 `.cnb.yml` 里的一行 `include: .cnb/git-sync.yml`。

## 适用判断

用户意图中出现下列任一信号即可触发：

- 给出一个参考上游项目地址（`https://github.com/<owner>/<repo>`），并要求「同步/拉取/镜像」到本仓库
- **只给出一个参考上游项目地址（或仅 `<owner>/<repo>`），没有任何其他文字** —— 地址本身就是指令，
  按「同步它」执行；**不要反问用户想干什么，也不要让他补一句「同步」**
- 要求「每天自动从参考项目更新」「跟随参考上游项目」「做参考项目镜像」
- 评论里点名了本仓库的地址（`https://cnb.cool/xgzwlkj/npc`，即「同步官」NPC）
  —— **这只是"点名说用谁"，不是必填咒语**：用户没写这句，一样要开工；
  反过来，用户写了这句但没给参考项目地址，才需要追问参考项目是谁

> 为什么裸地址也算触发：用户 `@` 本技能的核心场景就是「新项目上车」，
> 那时评论里往往只有一个参考项目链接。把它当成歧义去追问，等于让用户白跑一趟。
> 只有当评论里已是明确的**其他**诉求（提问、求助、非仓库地址）时才不按同步处理。

**不适用**：同步的是分支/tag 而非仓库、要求双向同步。遇到这些先说明限制。
私有参考项目可用（见「私有参考上游项目」一节）：运行环境有令牌即可，无令牌时按无权限处理并给出指引。

## 省 token 与省时间的做法（先读这段）

同步这件事本身很机械，**不要把时间和 token 花在"思考怎么同步"上**。三条硬规矩：

1. **默认走铺源，不要跑真实 merge 做首次落地。** 空仓库/首次同步一律走"铺源"：
   浅克隆一份参考项目快照，落成首个提交（不复刻参考项目历史）。这比"整仓 merge + 写入
   上万个文件"快得多，也少掉一大半工具调用。用户要的是"内容同步过来"，
   不是"把参考项目的几千条提交历史搬过来"。
2. **预设的流水线文件直接复制，不要自己重写。** `.cnb/git-sync.yml` 与
   `.cnb/sync-upstream.sh` **原样从技能仓库取**，只把地址/分支/频率
   填进去。绝对不要为了"适配"去重写脚本、也不要反复 sed/校验占位符 ——
   那是本技能已经验证过的文件。
3. **`<SEED_SOURCE>` 留着不用删。** 它只在"仓库还没有任何提交"时生效，
   之后自动失效，因此**不需要**为了"关掉它"再开一个 PR。少一次往返。

另外：

- **探测命令一次就够**，不要再跑 `du` / `git clone --bare` / `ls -R` / 大仓库试克隆。
  大型参考项目不要把整个仓库拉下来数文件 —— 那是几十 MB 流量换一个用不上的数字。
- **PR 正文用文件传**（`--body-file`）。用 `--body '<长文本>'` 会触发 shell
  转义与超长命令，容易报错重试，每次都白烧一轮上下文。
- **回复用户别复述技能文档**。三五行说清"做了什么 + PR 链接 + 怎么改/怎么停"就够了，
  长篇大论对用户没用，还会在后续每一轮里被重复读取。
- **改流水线脚本时注意 `set -e` 与管道的交互**（模板已修，别回退）：`X="$(cmd | awk ...)"`
  里 cmd 失败时，外层 `set -e` 会让**整个阶段静默退出**（日志一片空白、任务看不出原因），
  连自己的兜底分支都跑不到。所以：
  - 只做「信息性探测」的段；结果要能容错时，用 `set -uo pipefail`（**不开 errexit**），或给子命令 `|| true`
  - 需要重试的命令（如 `cnb pulls merge-pull`）必须写成 `out="$(cmd 2>&1 || true)"`，
    否则「重试 5 次」形同虚设，第一次 `checking` 被拒就把阶段掐掉了

## 输入

| 输入 | 必填 | 说明 | 缺省 |
| --- | --- | --- | --- |
| `UPSTREAM_REPO` | 是 | 参考上游项目 HTTPS 地址 | — |
| `UPSTREAM_BRANCH` | 否 | 参考项目分支 | 自动探测，回退 `main` |
| `TARGET_DIR` | 否 | 同步到哪个子目录 | 空 = 平铺到仓库根 |
| `CRON` | 否 | 同步频率（标准 POSIX cron） | **不写死**：默认每天一次（`17 3 * * *`），用户特别说明时才改 |

### 同步频率（`CRON`）

**默认一天一次，用户特别说明才改。**

- 用户没说频率 → 用默认 `17 3 * * *`（每天 03:17 一次），**不要**在脚本、模板
  注释、README 里把它写成「唯一支持」或「必须固定」的值
- 用户说了频率 → 按用户说的写。`CRON` 是标准 POSIX cron，**没有「每天只能一次」的限制**，
  说几次就写几次（多个时间点用 `,` 分隔）

| 用户说法 | CRON |
| --- | --- |
| （没说，默认）每天 1 次 | `17 3 * * *` |
| 每天 2 次（如 03:17 与 15:17） | `17 3,15 * * *` |
| 每天 2 次（如 09:00 与 21:00） | `0 9,21 * * *` |
| 每 6 小时 | `17 */6 * * *` |
| 每小时 | `17 * * * *` |
| 每周一 03:17 | `17 3 * * 1` |

注意：

- 时区固定 `Asia/Shanghai`，无需也不能在表达式里写时区
- 平台最小调度间隔 **5 分钟**，配得比 5 分钟还密的表达式提交会失败
- 用户说了「每天 N 次」但没说时间点，自己挑均匀间隔的时间点，
  并在 PR / 评论里写清楚，别回头再问
- 频率改了要同步改 README / PR 描述里「每天 03:17」这类字样，别留下对不上的旧描述

### 目标仓库的资源规格（`RUNNER_CPUS`）

同步任务本身很轻（拉取 + 合并），**按目标仓库的实际情况配，别一味要核数**：

- 默认 `cpus: 2`，够用；大仓库（历史多、pack 大）可抬到 `4`
- 不要写死成某个固定机型，`RUNNER_CPUS` 是替换 `.cnb/git-sync.yml` 时的占位符
- 首次同步大仓库、或参考项目 >1GB 时容易触发任务超时（默认 2 小时，最大 12 小时），
  这种仓库把 `timeout` 一起调大，并在 PR 里说明

### 判断用哪种模式

一条命令看明白（**只跑这一条**，别再补 `du`/`clone` 之类的探测）：

```bash
git log --oneline -1 2>/dev/null; echo "---"; ls -A
```

| 仓库情况 | 模式 | 配置 |
| --- | --- | --- |
| 没有提交（unborn HEAD）/ 就是要做参考项目镜像 | **铺源**（推荐） | `SEED_SOURCE=<参考上游项目>`、`TARGET_DIR=""` |
| 已有自己的项目，只想把参考上游项目放进来 | 子目录 | `SEED_SOURCE=<参考上游项目>`、`TARGET_DIR="<目录名>"` |
| 已经同步过（有参考上游项目 `.cnb/git-sync.yml`） | **只更新配置**，别重新同步 | 见下「已有同步配置的仓库」 |

- **铺源是最省的做法**：浅克隆快照落首个提交，跳过整仓历史。
  它和"平铺 + 真实 merge"的最终内容一致，保留路径（`.cnb.yml`/`.cnb/`/`.ci/`）一样不动。
- 目录名优先取参考上游项目仓库名（如 `ZCode`）；用户指定了就用用户的。
- 拿不准时看 Issue 里用户怎么说，仍不确定就在评论里问一句，别猜。

#### 已有同步配置的仓库：只复制配置，不要重新同步

如果仓库里已经有 `.cnb/git-sync.yml`（说明之前配过同步），**绝大多数"跟进"请求
只需要改配置**，不需要跑一次全量同步：

- 只改频率/分支/参考项目地址 → 拿最新模板，替换好占位符，**新增一个提交推上去**
- 不要为了"验证能跑"去执行一次全量同步：定时任务会自己跑，也随时能在流水线页面手动触发
- 不要重新跑一遍"全量搬运"：那是把一个已经同步好的仓库又整体重写一遍



## 执行流程

### 1. 载入依赖技能

本技能依赖 `cnb-api`（读写仓库/Issue/PR）与 `cnb-code-commit`（提交与建 PR）。若未加载，先加载。

### 2. 解析参数

从 Issue 里提取参考项目 URL。也支持用户只写仓库名（如 `zai-org/ZCode`），此时补全为 `https://github.com/zai-org/ZCode`。

规范化：去掉尾部 `.git` 和 `/`；校验形如 `https://host/<owner>/<repo>`。
不是合法 URL 时评论追问，不要瞎猜仓库地址。

### 3. 探测参考项目（一条命令，够用）

```bash
git ls-remote --symref <UPSTREAM_REPO> HEAD
```

- 成功 → 取 `HEAD` 指向的分支作为 `UPSTREAM_BRANCH`（输出里的 `ref: refs/heads/xxx HEAD`）
- 失败 → 先判私有还是网络：报 `Authentication failed` / `403` / `404` 大概率是私有仓库。
  此时检查运行环境有没有 `UPSTREAM_TOKEN`（见「私有参考上游项目」一节）：
  - **有令牌** → 用带令牌的 URL 重试 `ls-remote`（写法见下节），通了就按私有参考项目流程继续
  - **无令牌** → 评论告知用户：私有参考项目需要令牌（给出「私有参考上游项目」一节的指引），不要继续
  - 纯网络不通（超时/DNS）→ 告知用户并附原始报错，不要继续

**到此为止**。不要再跑 `git clone --bare`、`du -sh`、`find | wc -l` 之类的摸底 ——
同步脚本会自己处理分支、LFS 与体积问题；那些命令只是把大型参考项目下载几遍，
换一个用不上的数字。

### 4. 建分支、落盘脚本与配置（只落 2 个文件）

#### 4.0 先确定目标仓库的默认分支（空仓库必须在这里处理）

**`<BRANCH>` 占位符要填的是「目标仓库的默认分支名」，不是你想推的分支名。**

平台机制（踩过的真坑）：**push 一个不存在的分支名会让它在远端出现，
而空仓库的第一个远端分支就是该仓库的默认分支。**

- 同步官初装时推的是 `sync/bootstrap` → 默认分支被定成 `sync/bootstrap`
- 用户随后还得进「仓库设置」把它改回本仓库自己的默认分支
- 而定时任务挂在 `<BRANCH>` 上，默认分支不对时**整条无人值守链路都落空**

**空仓库上车时，默认分支跟随参考上游项目的默认分支。** 这是本技能的定位决定的：
用户要的是「clone 一份参考上游项目，然后自动跟随」——参考项目是 `master`，目标仓库就该是
`master`；我们不该自作主张把它改成 `main`。

解析优先级（就是 `<BRANCH>` 要填的值）：

| 情况 | 取哪个分支 |
| --- | --- |
| 目标仓库**已有任何远端分支** | 沿用现有默认分支，**绝不改写** |
| 空仓库 + `SEED_SOURCE` 非空 | **参考项目默认分支**（参考上游项目 `master` 就用 `master`） |
| 探测失败 / 没有 `SEED_SOURCE` | 回落兜底值：本仓库用 `main`（本仓库默认分支即 `main`） |

两条硬性注意（都是实测踩出来的）：

1. **`CNB_DEFAULT_BRANCH` 不能当第一优先级。** 实测在空仓库 runner 上它
   **已经预设成某个值**。若直接信它，「参考项目是 master」永远算不出来，
   绕一圈又回到兜底值（那是**平台的**默认，不是**目标仓库的**默认）。
   只有当**本地确实已有分支、仓库自己声明过默认分支**时，才把它当用户的选择。
2. **别用 sed 捕获组取分支名。** `git ls-remote --symref` 的输出是
   `ref: refs/heads/master\tHEAD`（tab 分隔），sed 会把尾部 tab 一起吞进分支名，
   push 出去的 ref 就带脏字符。用 awk 按字段切分：

   ```bash
   UP_SDB="$(git ls-remote --symref <参考上游项目> HEAD 2>/dev/null \
     | awk '/^ref: refs\/heads\// { sub("refs/heads/", "", $2); print $2; exit }')"
   ```

处理办法：`.cnb/git-sync.yml` 里带了两个阶段（定时流水线最前面，都在
`fetch-and-merge-upstream` 之前）：

- `resolve-default-branch` —— 按上表算出分支名，写进 `.git/sync-default-branch`
- `init-default-branch` —— **只在**「仓库还没有任何远端分支」时动作：
  读上一步的结果，把默认分支先建成它，之后所有 push（引导分支、临时分支、PR 合并）
  都会顺理成章地进到这个分支

所以同步官要做的只有两件事：

1. `<BRANCH>` 填**上面表格算出来的那个分支名**，并且**在建引导分支
   `sync/bootstrap` 之前**先把这个默认分支建出来 ——
   否则占位符与真实默认分支会对不上：

   ```bash
   UP_SDB="$(git ls-remote --symref "<参考上游项目>" HEAD 2>/dev/null \
     | awk '/^ref: refs\/heads\// { sub("refs/heads/", "", $2); print $2; exit }')"
   DESIRED="${UP_SDB:-${CNB_DEFAULT_BRANCH:-main}}"
   # 空仓库（origin 还没有任何分支）时先建默认分支，再开引导分支
   if [ -z "$(git ls-remote --heads origin 2>/dev/null)" ]; then
     git commit -q --no-gpg-sign --allow-empty -m "chore: 初始化默认分支 ${DESIRED}"
     git push -f origin "HEAD:refs/heads/${DESIRED}"
   fi
   ```

   > 分支名最终以**实际建出来的那个**为准：算出 `DESIRED` 之后就用它，
   > 别另算一遍，否则 `<BRANCH>`、`init-default-branch` 与真实默认分支三者会对不上。

2. 在 PR 描述与评论里写明分支是怎么定的：
   - 仓库**已有**分支 → 「沿用现有默认分支 `<分支>`，未做改动」
   - 空仓库上车 → 「默认分支已按参考上游项目跟随初始化为 `<分支>`」

   两种情况下用户都不需要再去仓库设置里改。

仓库**已经有**默认分支时，这一步什么都不做 —— 绝不去改写用户已有仓库的分支结构。

在当前仓库开分支 `sync/bootstrap`（已存在则复用并 fast-forward），把两个文件写进去：

- `.cnb/sync-upstream.sh` ← 取自本技能目录 `scripts/sync-upstream-target.sh`
- `.cnb/git-sync.yml` ← 取自本仓（NPC 所属仓库，`${CNB_NPC_SLUG:-xgzwlkj/npc}`）的 `.ci/git-sync.yml` 模板

**目标仓库到此只多 2 个文件**（外加 `.cnb.yml` 里的一行 include），这就是「最小文件落地」。
不要引入第三个文件，也不要在目标仓库里再建一层脚本目录。

**这两个文件不要重新发明**，直接取参考项目版本、只替换占位符，保证与技能仓库同步演进。取文件：

```bash
# `cnb git get-raw` 的输出是 YAML 包了一层的（前面有 status/contentType/data 头，
# data 里才是文件内容）。**不能直接 `> 文件`** —— 那样写进去的是个带头的废文件，
# 后面 bash 执行时会报 `status:: command not found` 这类错。必须把 data 解出来。
fetch_raw() {   # $1=ref-with-path（不含仓库名，仓库固定为本仓 NPC slug）
  # 解 data 层优先用 jq —— 本仓 NPC 镜像（Dockerfile）只装了 jq，**没有 python3**，
  # 写成只认 python3 会在真实运行环境里直接 command not found。
  # 没有 jq 时再退回 python3（本地开发机常有），两者逐字节等价（jq 用 -j 去尾换行）。
  cnb git get-raw --repo "${CNB_NPC_SLUG:-xgzwlkj/npc}" --ref-with-path "$1" \
    | sed -n '/^data: /,$p' | sed '1s/^data: //' \
    | { if command -v jq >/dev/null 2>&1; then jq -j '.'
        elif command -v python3 >/dev/null 2>&1; then python3 -c 'import sys,json; sys.stdout.write(json.load(sys.stdin))'
        else echo "❌ 解 data 层需要 jq（NPC 镜像已内置）或 python3，二者都没有" >&2; exit 1
        fi; }
}

fetch_raw main/skills/sync-upstream/scripts/sync-upstream-target.sh > .cnb/sync-upstream.sh
fetch_raw main/.ci/git-sync.yml                                     > .cnb/git-sync.yml

# 取回后**立刻自检**：内容不正确就不许提交
bash -n .cnb/sync-upstream.sh \
  || { echo "❌ .cnb/sync-upstream.sh 不是合法 shell（多半把 YAML 头也写进去了）"; exit 1; }
head -1 .cnb/sync-upstream.sh | grep -q '^#!/usr/bin/env bash' \
  || { echo "❌ .cnb/sync-upstream.sh 内容不对（应以 shebang 开头）"; exit 1; }
grep -q '^<BRANCH>:' .cnb/git-sync.yml \
  || { echo "❌ .cnb/git-sync.yml 内容不对（应含未替换的 <BRANCH> 占位符）"; exit 1; }
```

替换 `.cnb/git-sync.yml` 中的占位符，**注意分支名也要一起替换**：

| 占位符 | 替换为 |
| --- | --- |
| `<BRANCH>`（顶层 key） | **目标仓库实际会有的那个默认分支名**，按第 4.0 步的优先级算出来（仓库已有分支就填它；空仓库上车就填**参考项目默认分支名**），**必须替换，别留着**。空仓库时模板里的 `resolve-default-branch` + `init-default-branch` 两个阶段会把它建出来 |
| `<CRON>` | `17 3 * * *`；用户要每天两次就写 `17 3,15 * * *`（见「同步频率」） |
| `<UPSTREAM_REPO>` | 参考项目地址 |
| `<UPSTREAM_BRANCH>` | 参考项目分支 |
| `<TARGET_DIR>` | 目标子目录；平铺模式留空字符串 `""` |
| `<RUNNER_CPUS>` | 任务 CPU 核数，默认 `2`；大仓库抬到 `4`（同步任务很轻，别一味要核数） |
| `<BOOTSTRAP_BRANCH>` | 引导分支名，**与第 4 步建的分支名一致**（如 `sync/bootstrap`）。它让「引导 PR 合并后自动删掉该分支」，避免那个 PR 一直挂着没人处理；见下文「引导 PR 必须自我了结」 |
| `<SEED_SOURCE>` | 就填参考项目地址。它只在「仓库还没有提交」时生效（铺源），之后自动失效 —— 所以**同步完不用删、不用再开 PR** |

替换完自检一遍：`<BRANCH>` / `<CRON>` 等尖括号占位符**一个都不能残留**，
否则定时任务会因为分支名非法而整条不生效。（只查一次；不要反复 sed + 校验。）

### 私有参考上游项目（可选令牌通道）

私有参考项目的拉取凭证**来自运行环境注入的环境变量**（单一通道，零模板改造）：

- 同步官的运行环境已由本仓事件流水线 `imports` 密钥仓库注入
  `CNB_MIRROR_TOKEN`（CNB 参考上游项目）/ `GH_TOKEN`（GitHub 参考上游项目）。
  同步脚本自动收编二者作为 `UPSTREAM_TOKEN`（显式 `UPSTREAM_TOKEN` 优先），
  临时改写拉取 URL、fetch 完立即还原——令牌不落代码、不进日志。
- 目标仓库的定时任务默认**不含任何令牌**（模板零密钥引用）。
  若目标仓库的流水线也需要拉私有参考项目，由引用方自行在 `.cnb/git-sync.yml`
  的 `env` 段注入 `UPSTREAM_TOKEN`（模板 env 段已留注释占位行）——
  来源不限（如密钥仓库 `imports`），写法由引用方决定，本技能不做约定。

带令牌探测/拉取的 URL 写法（与脚本内置一致，仅临时使用）：

```bash
git ls-remote https://x-access-token:${UPSTREAM_TOKEN}@<host>/<owner>/<repo> HEAD
```

然后在当前仓库 `.cnb.yml` 里追加 include（文件已存在就追加这一行，不要覆盖原内容）：

```yaml
include:
  - .cnb/git-sync.yml
```

#### 交付前不需要碰「保护分支」，也不许让用户去设（重要）

**曾经的错**：早期版本把「默认分支是保护分支 + 勾选需要评审人批准」写成了自动合并的
前置条件，于是交付时总要附一句「请去仓库设置里开一下保护分支」。用户的原话是：

> 「我不是说了需要自动处理 pr，不要人工去处理，全程无人值守」

让用户去点设置，本身就不是无人值守。而且这条路根本走不通 ——
**NPC 的 token 没有 `repo-manage:rw` 权限**，无法替用户创建保护分支规则，
实测调用会直接返回：

```text
status: 403  errcode: 10023
errmsg: The token's authorization scope does not match this request.
        Missing required scopes: repo-manage:rw
```

**现在的做法**：合并动作内联在定时流水线里，不使用 `pull_request.mergeable`：

```bash
# 开完 PR，就地把它合掉。终态由平台自己保证，不需要保护分支、不需要评审人。
cnb pulls merge-pull --repo "$CNB_REPO_SLUG" --number "$PR_NO" \
  --merge-style squash --commit-title "$TITLE"
```

三个要点（模板已实现，改的时候别退化）：

1. **`--commit-title` 是必填**。缺了会返回 `400 errcode: 2000001 commit_title is required`
2. **要重试**。PR 刚创建时平台还在做可合并性检查（`mergeable_state: checking`），
   此刻合并会被拒 —— 这是瞬态，退避重试即可，别当失败
3. **只合并本轮自己开的那个 PR 编号**（`post-pull` 的输出里 `number` 是字符串，
   用 awk 取出后 `set-output` 传给下一阶段）。人在仓库里提的 PR 一律不动

保护分支**如果本来就有**，`pull_request.mergeable` 那条兜底流水线也会触发，
但它只是复核式地再跑一次（PR 早已合并，幂等落空）。有没有都不影响无人值守。

两条实测出来的、别写成"等价"的事实：

- **兜底流水线只在「默认分支恰好是保护分支」时才被平台触发。** 目标仓库的默认分支是
  跟随参考上游项目建的（参考上游项目 `master` 就是 `master`），而仓库的保护分支设置未必跟着走；
  那种情况下兜底路径是哑的。**这不是缺口**：主路径是内联 `merge-pull`，
  不依赖任何平台事件。所以也别去查保护分支、别让用户设。
- **合并后 PR 的源分支会被平台自动删除**（实测：合并时连同源的 `DeleteEvent` 一起发出，
  分支随后就不在远端了）。所以模板里**不需要**再配
  `--delete-source-branch` / `removeSourceBranch` 之类的东西；临时分支
  `sync/upstream-auto-<时间戳>` 不会在仓库里堆积。

因此交付时**不要**再去查保护分支、也**不要**在评论里让用户设置任何东西。

### 5. 首次同步（铺源路径）

```bash
git config user.name  "cnb-sync-bot"
git config user.email "cnb-sync-bot@users.noreply.cnb.cool"

UPSTREAM_REPO="<参考项目地址>" \
UPSTREAM_BRANCH="<参考项目分支>" \
TARGET_DIR="<目标目录，平铺则留空>" \
SEED_SOURCE="<参考项目地址>" \
bash .cnb/sync-upstream.sh
```

`SEED_SOURCE` 是**空仓库首次上车的快捷路径**：浅克隆一份参考项目快照直接落成首个提交，
不复刻参考项目的提交历史。比"合并整个参考项目历史"快很多，内容和"平铺"完全一致。

> 万一这个仓库已经有历史、或与参考上游项目没有共同祖先，脚本会自己判断并走对应的
> 安全路径（快照式/真实 merge），**不需要**你手工干预或预先分析历史关系。

看脚本输出的 `##[set-output SYNC_STATUS=...]`：

- `merged` → 成功，继续下一步
- `no-update` → 参考项目内容与本地一致，照样继续（PR 里说明即可）
- `fetch-failed` → 网络或权限问题，评论告知用户后停止
- `conflict` → 冲突。检查是否为平台配置文件冲突；若只是 `.cnb.yml` 冲突，用本地版本覆盖后重跑。其他文件冲突则评论列出冲突文件，请用户决定取舍
- `empty` → 参考上游项目导出后为空（极少见），评论告知后停止
- `skipped` → 参考项目改动与本地并发改动重叠，本地版本保留、参考项目改动跳过；在 PR/评论里点出重叠文件

### 6. 提交并建 PR

```bash
git add -A
git commit -m "chore: 跟进参考上游项目 <upstream-repo> 并配置每日自动更新"
git push origin HEAD:sync/bootstrap

# PR 正文写进文件再传：用 --body '<长文本>' 会踩 shell 转义与超长命令
cat > /tmp/pr-body.md <<'EOF'
...（下面 6 点）...
Ref: #<本仓库 Issue 编号>
EOF
# 记下 PR 编号，紧接着就把它合掉（见下）
PR_NO="$(cnb pulls post-pull --repo "$CNB_REPO_SLUG" \
  --title "chore: 跟进参考上游项目 <upstream-repo>" \
  --head sync/bootstrap --base "$CNB_DEFAULT_BRANCH" \
  --body-file /tmp/pr-body.md \
  | awk '$1=="number:" { gsub(/\"/,"",$2); print $2; exit }')"
```

> 引导分支名要与模板里 `<BOOTSTRAP_BRANCH>` 的值一致（都用 `sync/bootstrap`），
> 否则引导 PR 合并后不会被自动收尾。

#### 建完引导 PR 就地合并，别把它留给用户

初装的引导 PR 是个例外：它合并之前，定时任务还不存在，**没人会来合它**。
用户曾经就是因为这个 PR 一直挂着而质问「为什么这里还是有一个 PR 并没有处理」。

所以**建完立刻自己合掉**，全程不留给用户任何待办：

```bash
cnb pulls merge-pull --repo "$CNB_REPO_SLUG" --number "$PR_NO" \
  --merge-style squash --commit-title "chore: 跟进参考上游项目 <upstream-repo> 并配置自动更新"
```

- `--commit-title` **必填**（缺了报 `400 commit_title is required`）
- 刚创建时 `mergeable_state` 可能是 `checking`，合并会被瞬态拒绝 ——
  退避重试几次（`sleep 5`），别当失败
- 合并成功后由 `pull_request.merged` 流水线自动删掉 `sync/bootstrap` 分支，
  仓库里不会留下孤儿分支，也不会留下任何待人工处理的 PR
- 合并这一步需要 `repo-pr:rw`。NPC token 默认就有（实测可用）；
  若真的拿到 `403`，退回到「开 PR + 在评论里点明需要合并」即可，不要卡死流程

PR 描述里必须写清：

1. **参考上游项目**：仓库地址 + 分支 + 同步到的 commit（短 SHA）
2. **同步模式**：平铺 / 子目录 `<dir>`
3. **自动更新**：cron 时间、由哪条流水线执行
4. **自动合并**：之后每天由流水线自动开 PR 并自动合并，不再需要人工，也不需要在仓库设置里配任何东西
5. **保留了什么**：`.cnb.yml`、`.cnb/` 未被参考上游项目覆盖
6. **怎么调整**：改哪儿能换时间 / 换分支 / 停用
7. **怎么手动触发一次**：重跑该流水线
8. **合并后不需要再管**：引导 PR 由同步官建完即自动合并（不需要用户点合并）；
   引导分支随后由 `pull_request.merged` 流水线自动删除，不会留下任何待人工处理的 PR

提交规范参考 `cnb-code-commit`。**禁止**直接推 `main`。

Issue 评论**三到五行封顶**，别写长篇报告、别复述技能文档：

- 一句话结论 + PR 链接
- 落地文件数（`2 个`）+ 自动更新频率（如"每天 03:17"）

## 三种落地方式（脚本自己选，你不用管）

| 方式 | 何时用 | 提交历史 | 保留路径 |
| --- | --- | --- | --- |
| **铺源** | 空仓库 / 与参考上游项目毫无共同祖先（**推荐**） | 只落一个提交，不复刻参考项目历史 | 不动 |
| 快照式 | 本地与参考上游项目各有一批提交、但从未真正合过（老镜像） | 只落一个提交 | 不动 |
| 真实 merge | 已有共同祖先（正常增量同步） | 保留参考项目历史，可三方合并 | 不动 |

三种方式的**内容语义一致**：受保护路径（`.cnb.yml`、`.cnb/`、`.ci/`）永远不被参考上游项目覆盖，
其余文件按参考项目快照对齐（新增写入、修改覆盖、删除同步删除），每次提交都带
`Upstream-Sync: <sha>` 标记。

### 为什么"无共同祖先"时不能硬用 `git merge`

这是本技能踩过的真坑，改动时别退回去：

- 没有共同祖先时，同名文件在 git 眼里全是 `add/add` 冲突
- `-X ours` 会把这类冲突**一律判给本地** —— 于是"参考上游项目删除的文件"会被当成
  "本地保留的文件"，参考项目的改动被静默丢掉，脚本却报同步成功
- 脚本因此只在**确有共同祖先**时才走真实 merge；否则用快照式（整树对齐）

### 增量同步与"重叠改动"

- 真实 merge 时，若**本地对某文件有并发提交**而**参考上游项目也改了同一个文件**，
  本地版本胜出、参考项目改动被跳过。脚本不会静默忽略：
  列出重叠文件名并把状态置为 `skipped`；流水线 `report` 阶段打 ⚠️ 提示
- 想采纳参考项目版本，先撤销本地对这些文件的改动，再重跑同步
- `Upstream-Sync` 标记是"上次同步到哪个参考上游项目提交"的游标。
  **不要手工删这个标记行**

### 两个脚本同口径（采集版 / 下发版）

上面这套 LFS 处理，**采集版（`scripts/sync-upstream.sh`）与下发版
（`scripts/sync-upstream-target.sh`）行为一致** —— 同一份技能不该有两套脾气。
下发版覆盖两个入口，两个都做探测 + 还原 + 「拿不到就中止」：

| 入口 | 何时走 | 参考上游项目真身从哪里拉 |
| --- | --- | --- |
| 铺源（`SEED_SOURCE`） | 目标仓库还没有提交（首次上车） | `git fetch <参考上游项目> HEAD` 进本仓库后，从本仓库对象库/缓存取 |
| 浅克隆（默认） | 目标仓库已有提交（**定时任务每天走的就是它**） | staging 临时克隆里（持有 `origin` 的那侧） |

实现要点（沙箱实测，改代码前先读）：

- `git lfs fetch <名字> <ref>` 的「名字」必须是**具名 remote** 或地址形态，
  传裸 ref 会报 `Invalid remote name`；地址形态必须带上显式 `<ref>`
  （单参数 `git lfs fetch <URL>` 会静默「0 objects found」）。
- 探测/拉取必须在**持有参考项目的那一侧**执行。clone 路径下参考上游项目在 staging 目录里，
  拿目标仓库的 `HEAD` 去探测永远探不到 LFS —— 这是实际踩过的坑。
- 文件在**仓库之外**（staging 临时目录）时 `git lfs checkout <路径>` 不生效，
  唯一可靠的兜底是从本地 LFS 缓存按 oid 拷贝真身。
- 浅克隆要带 `GIT_LFS_SKIP_SMUDGE=1`：否则参考项目 LFS 对象拉不到时 clone 会在
  中途 `smudge filter lfs failed` 硬失败（退出码 128），既拿不到可读结论，
  也不是我们要的「中止」语义。

## 子目录模式的行为细节

- 每次同步是**整体替换** `TARGET_DIR/`：参考上游项目新增的写入、修改的覆盖、**删除的同步删除**
- `TARGET_DIR` 之外的文件一律不动
- 参考上游项目自带的 `.cnb/`、`.cnb.yml`、`.ci/`、`.github/workflows/` 会被剔除，不写进来
- 每次同步落一条 `chore: 跟进参考上游项目 <sha> → <dir>/` 提交，正文同样带 `Upstream-Sync: <sha>` 标记
- 因此**不要**在 `TARGET_DIR` 里做本地改动——下次同步会被覆盖。要改就去参考上游项目改

## Git LFS 参考上游项目：自动处理，不需要用户声明

**用户不需要知道自己要同步的是不是 LFS 大文件项目。** 脚本会自动探测、自动处理。

### 探测方式（无需 LFS 服务器）

看参考上游项目树里有没有 LFS 指针文件即可，纯本地 `git` plumbing 完成：

- 指针文件特征：体积 < 1024 字节，且内容以
  `version https://git-lfs.github.com/spec/v1` 开头
- 命中即判定为 LFS 项目，并把命中的路径列出来

探测结果会打印在日志里：`检测到参考项目使用 LFS：N 个文件`；
同时通过 `##[set-output SYNC_LFS=<0|1>]` 传给流水线。

### 同步行为

| 环节 | 处理方式 |
| --- | --- |
| 导出快照 | 统一用 `GIT_LFS_SKIP_SMUDGE=1 git archive` 稳定产出**指针文件**，避免 git-lfs filter 在归档中途失败把整个同步炸掉 |
| 还原真身 | `git lfs fetch --all` + `git lfs checkout`；对象已在本地缓存但文件在仓库外（如 staging 临时目录）时，直接按 oid 从本地 LFS 缓存拷贝 |
| 入库方式 | 自动执行 `git lfs track`，让**真身以 LFS 指针入库**，而不是把几百 MB 的大文件当普通 blob 塞进对象库（否则仓库体积会爆） |
| 跟踪规则 | 参考项目的 `.gitattributes`（`filter=lfs` 规则）会随文件一起同步过来 |

### 关键点：拿不到真身就中止，绝不假装成功

如果 LFS 真身内容拉不下来（参考项目 LFS 对象拉不到——私有未配令牌、或环境缺 git-lfs）：

- 状态置为 **`conflict`**，**中止本次同步，不提交任何内容**
- 明确打印原因与处理建议

**为什么必须中止**：落盘 131 字节的指针文件看起来「同步成功」，
但实际内容已经丢了；更糟的是下次同步会把这个 commit 当成「已同步到该参考上游项目
commit」，从此永远不再重试 —— 用户拿到一个空壳仓库却毫不知情。

### 用户怎么问就怎么答

| 用户问 | 回答 |
| --- | --- |
| 「参考项目是不是 LFS 项目？」 | 不用管，脚本自动探测，是就自动按 LFS 处理 |
| 「同步后大文件怎么只有 131 字节？」 | 那是 LFS 指针，说明没能还原真身。脚本本应中止并报 `conflict`；若真出现指针落盘，检查参考项目 LFS 对象是否可拉取（公开匿名 / 私有走令牌） |
| 「同步报 conflict，说是 LFS」 | 参考项目的 LFS 对象拉不到。让用户确认参考上游项目仓库的 LFS 对象是否公开可读 |
| 「大文件会不会把仓库撑爆？」 | 不会。真身以 LFS 方式入库，仓库里只存指针 + 平台侧的 LFS 存储 |

### 如果目标环境缺 git-lfs

脚本会检测不到真身、按上面的规则中止并报 `conflict`（**不会**退化成把指针
当成功）。需要用户为 runner 镜像补上 `git-lfs`，或联系参考上游项目确认托管方式。

## 引导 PR 必须自我了结（配了无人值守之后，别留一个挂着的 PR）

**这是真实踩过的坑，交付前必须确认。**

同步官初装时会开一个 PR（源分支 `sync/bootstrap`，即"引导 PR"）。这个 PR 提交的
`.cnb/git-sync.yml` **已经带了定时任务和自动合并配置** —— 它一合并，目标仓库立刻进入无人值守。

问题在于：**之后只有「参考项目有更新」才会开新 PR。** 如果参考上游项目当前内容与仓库一致，
定时任务的状态是 `no-update`：不推送、不开 PR。此时**没有任何人去合并那个还开着的引导 PR**，
它就一直挂在 PR 列表里等人处理。用户的原话是：

> 「为什么这里还是有一个 PR 并没有处理」

### 怎么收口（模板已内置，别拆掉）

下发的 `.cnb/git-sync.yml` 里带了第三条流水线：

```text
pull_request.merged            ← 任一 PR 合并后触发
  └─ bootstrap-pr-self-resolve
     if 源分支名 == ${BOOTSTRAP_BRANCH}（即 sync/bootstrap）
        → git push origin --delete <该分支>   清理引导分支
```

- **只认引导分支名**（精确相等，不用前缀匹配，免得误伤同名前缀的分支）
- **不看评审**：这是机器人开的自家 PR，要的是"合并即生效、随后无人值守"。
  如果按 `pull_request.mergeable` 走，又会卡在"需要评审人批准"上
- 引导分支删掉后，控制权完全交给 crontab：之后一律自动跑、自动开 PR、**自动合并**
  （而且初装时引导 PR 就已经被同步官自己合掉了，用户全程不需要点任何东西）

### 交付时你要做的两件事

1. **`<BOOTSTRAP_BRANCH>` 必须填**，值等于第 4 步建的分支名（`sync/bootstrap`）。
   留空不会影响定时任务，但会失去"引导分支自我清理"，仓库里会多留一个孤儿分支
2. 建完引导 PR **立刻自己合并它**（见第 6 节），再把结论写进评论 ——
   不能让引导 PR 挂在那里等用户处理，那就是"要人工"了

### 别再发明"自动合并一切 PR"

有人会想"干脆把 `pull_request.mergeable` 改成不限源分支，谁合并都自动合"。不要这么做：
那会把人提的正常 PR 也自动合掉，抢了人工评审的活。收口只针对引导分支这一条。

## 无人值守：全自动合并（默认行为）

**用户要的最终效果是「配一次，之后再不管」。** 所以下发的 `.cnb/git-sync.yml`
里已经写好了自动合并，不需要你额外做什么：

```text
定时任务（crontab）
  ├─ sync-upstream.sh         拉参考项目、有更新才落地（无更新就地结束）
  ├─ open-auto-merge-pr       有变更：推临时分支 sync/upstream-auto-<时间戳>
  ├─ create-auto-merge-pr     用 cnb pulls post-pull 开 PR，输出 PR 编号
  ├─ merge-pr-inline          就地 merge-pull 合掉它 ← 无人值守的真正收口
  └─ report                   汇报状态

pull_request.mergeable         （兜底）默认分支恰好是保护分支时才会触发
  └─ git:auto-merge            只合并源分支名带 sync/upstream-auto 前缀的 PR
```

### 三个关键设计

1. **只在真的有更新时才开 PR**。无更新时 `sync-upstream.sh` 退出码为 `no-update`，
   后面的推送/开 PR 阶段都被 `if` 跳过 —— 不会每天都堆一个空 PR。
2. **每次用带时间戳的独立分支**（`sync/upstream-auto-<UTC 时间戳>`），
   不复用旧分支，避免历史被带歪，也便于在流水线记录里对上号。
3. **只自动合并「自己开的」PR**。`git:auto-merge` 阶段带了
   `if: 源分支名以 sync/upstream-auto 开头`，人在这个仓库提的正常 PR 一律不动，
   不抢人工评审的活。

### 前置条件：没有前置条件

**不需要保护分支，不需要评审人，不需要用户去仓库设置里点任何东西。**

早期版本把「保护分支 + 需要评审人批准」当作前置条件，结果是把活推给了用户；
而且这条路对 NPC 根本走不通（token 没有 `repo-manage:rw`）。现在改成：

```text
定时任务（crontab）
  ├─ sync-upstream.sh       拉参考项目，有更新才落地（无更新就地结束）
  ├─ open-auto-merge-pr     推临时分支 sync/upstream-auto-<时间戳>
  ├─ create-auto-merge-pr   开 PR，并把 PR 编号传给下一阶段
  ├─ merge-pr-inline        ← 就地 merge-pull 合掉它（无人值守的真正收口）
  └─ report                 汇报状态
```

保护分支**如果本来就有**，`pull_request.mergeable` 那条兜底流水线也会触发，
只是复核式地再跑一次（PR 早已合并，幂等落空）。有没有都不影响无人值守。

**合并失败怎么办**：`merge-pr-inline` 重试 5 次仍不成功时明确报错，
并打印 PR 链接 —— 同步内容已经安全落在临时分支上，不会丢；重跑流水线即可。

手动同步时同样**不需要**查保护分支，见上面「交付前不需要碰『保护分支』」。

### 用户问起来怎么答

| 用户问 | 回答 |
| --- | --- |

## 边界与限制

- **公开参考项目开箱即用；私有参考项目走令牌通道**。同步官运行环境已注入 `CNB_MIRROR_TOKEN`/`GH_TOKEN`
  （脚本自动收编为拉取凭证），多数私有参考项目**零配置**；环境无令牌时按无权限处理并给出指引
  （见「私有参考上游项目」一节）。匿名路径行为与公开参考项目完全一致
- **默认一天一次，频率可调（≥5 分钟一次）**。用户没特别说明就用每天一次（`17 3 * * *`）；
  用户说了就按用户说的改 `CRON`（每天两次写 `17 3,15 * * *`）。
  CNB 定时任务最小间隔 5 分钟，**没有每天只能一次的限制**
- **定时任务负责人是最后修改配置的用户**。如果该用户被移出仓库，定时任务会失败——PR 里提示一句
- **改频率要重新触发一次同步**：`crontab` 属于 `include` 进来的模板文件，CNB 只在目标分支
  有 **push** 时重新解析定时任务。所以改 `CRON` 必须 push 到目标分支（PR 合并即可），
  否则新增/删除的时间点不会生效
- **只同步指定分支**。不会自动跟随参考上游项目新增的 tag 或 release。
  但「指定分支」的默认值就是**参考项目的默认分支**（见第 4.0 步）
- **不会凭空创建分支**：脚本不传 `TARGET_BRANCH` 就只在本地提交；
  空仓库上车的默认分支跟随参考上游项目，不会莫名多出一个 `main`
- **无人值守没有任何前置设置**：合并由流水线内联 `merge-pull` 完成，
  不需要保护分支、不需要评审人、不需要用户进仓库设置。唯一用得到保护分支的地方是
  `pull_request.mergeable` 兜底路径，而它可有可无
- **NPC token 无 `repo-manage:rw`**：所以从来不要尝试替用户创建保护分支规则（会 403）。
  合并走 `repo-pr:rw`（`cnb pulls merge-pull`），实测可用
- **内联合并失败不会丢内容**：同步结果已落在临时分支上，日志会给出 PR 链接；
  重跑流水线或手动合并即可
- **合并后临时分支由平台自动删除**：实测 CNB 在合并 PR 时会一并删掉源分支
  （合并事件之后紧跟着同源的 `DeleteEvent`）。因此 `sync/upstream-auto-<时间戳>`
  不会在仓库里越堆越多，也不需要额外配置
- **模板里的「信息性探测」段不许开 errexit**：`X="$(cmd | awk ...)"` 里 cmd 失败时，
  `set -e` 会让整个阶段**静默退出**（日志空白）。这类段必须用 `set -uo pipefail`
  或给子命令加 `|| true`；需要重试的命令必须写成 `out="$(cmd 2>&1 || true)"`
- **默认分支由流水线初始化，且空仓库时跟随参考上游项目**：空仓库的默认分支由
  `resolve-default-branch` + `init-default-branch` 两个阶段建出来 ——
  分支名优先跟随**参考项目默认分支**（参考上游项目 `master` 就建 `master`），
  探测不到才回落 `main`。所以既不会出现「默认分支被定成 `sync/bootstrap`、
  还要去设置里改」，也不会把参考项目的 `master` 自作主张改成 `main`；
  仓库已有分支时这两个阶段不做任何事，不会改写用户已有仓库的分支结构
- **引导 PR 会自我了结**：引导分支（`<BOOTSTRAP_BRANCH>`）上的 PR 合并后由流水线自动删除该分支；
  这是为了不让它一直挂着等人处理。仅限该分支，其他 PR 一律不动
- **不做反向同步**。本地改动不会推到参考上游项目（脚本已把 upstream 的 push URL 设成 `no-push://disabled`）
- **LFS 参考上游项目自动处理**，用户无需声明。参考项目 LFS 对象须可拉取（公开匿名 / 私有走令牌）；
  拉不到时会中止并报 `conflict`，不会提交指针文件（见上文「Git LFS 参考上游项目」）
- **CNB_TOKEN 范围限制**：NPC 事件下 token 默认仅限当前仓库。本流程的所有操作（读技能仓库文件、写当前仓库、建 PR）都在允许范围内；若需要跨仓操作，需组织开启「允许 NPC 跨仓操作」
- 参考上游项目仓库体积极大（>1GB）时首次同步可能超时（任务默认上限 2 小时、最大 12 小时），
  这种仓库把 `RUNNER_CPUS` 抬到 `4` 并放宽 `timeout`。
  铺源路径用的是 `--depth 1` 浅克隆，已经比整仓克隆省很多，先按默认配置跑

## 常见追问速答

- **「同步完成了，以后要手动吗」** → 不用，每天 `<CRON>` 自动跑，有更新才提交
- **「怎么立刻同步一次」** → 到仓库流水线页面重跑 `sync-upstream`，或把 cron 临时改到最近的时间点
- **「能每天同步两次吗」** → 能。默认是每天一次，用户说了就改成 `17 3,15 * * *`
  （每天 03:17 与 15:17 各一次），见上文「同步频率」。改完要把改动合进目标分支才会生效
- **「要多少核 / 什么机型」** → 同步任务很轻，`cpus: 2` 够用；本技能自身就建议跑在 2C4G 机型上。
  只有参考上游项目仓库特别大（历史长、pack 大）时才抬到 `4` 并放宽 `timeout`
- **「之后要手动合并吗 / 怎么全自动」** → 不用手动。之后每次更新都由流水线开 PR
  并在同一轮流水线内自动合并，全程无人值守，也不需要在仓库设置里配任何东西
- **「为什么还有个 PR 挂着没人处理」** → 老版本的行为，已修。引导 PR 现在由同步官
  建完即自己合并；参考上游项目没更新时也不会再堆空 PR。历史遗留的挂起 PR 手动合一次即可，
  之后不会再出现
- **「参考项目是私有仓库，能同步吗」** → 能，多数场景零配置：同步官运行环境已注入令牌
  （`CNB_MIRROR_TOKEN`/`GH_TOKEN`），脚本自动带凭证拉取。目标仓库的**定时任务**默认
  不带令牌——若它也需要拉私有参考项目，由引用方在 `.cnb/git-sync.yml` 的 env 段注入
  `UPSTREAM_TOKEN`（见「私有参考上游项目」一节）
- **「怎么停用」** → 从 `.cnb.yml` 移除 `include: .cnb/git-sync.yml` 那一行
- **「能同步另一个仓库吗」** → 能，同一个仓库可加多条 cron（`lock.key` 用不同的值避免互相阻塞），或复制一份 `.cnb/git-sync.yml` 换名字
- **「参考项目是 LFS 大文件项目怎么办」** → 不用做任何额外配置。脚本自动探测并按 LFS 同步，
  真身以 LFS 方式入库，`.gitattributes` 规则一并带过来
- **「LFS 同步报 conflict 了」** → 参考项目 LFS 对象拉不到。确认参考项目 LFS 对象是否可拉取（公开匿名 / 私有走令牌，见「私有参考上游项目」一节）；
  脚本不会提交指针文件，所以不会造成静默丢内容
- **「新仓库的默认分支被弄成了 sync/bootstrap / 还要去设置里改」** → 老版本的行为，已修：
  模板新增 `init-default-branch` 阶段，空仓库首次推送前先把默认分支建成 `<BRANCH>`。
  已有的旧仓库（默认分支已被带歪）只需在「仓库设置」里把默认分支改成 `<BRANCH>`，不用改配置
- **「参考上游项目仓库的默认分支不是 main 怎么办」** → **空仓库上车时默认分支跟随参考上游项目**：
  参考项目默认分支是 `master`，目标仓库就建 `master`，不会被我们改成 `main`。
  解析优先级见第 4.0 步（仓库已有分支 → 沿用；空仓库 → 跟随参考上游项目；探测不到 → `main`）。
  仓库已经有分支的，一律沿用不动
- **「为什么建出来的不是 / 不是 main」** → 就是故意的：这个 NPC 的定位是
  「clone 一份参考上游项目，然后自动跟随」，默认分支同名才对得上；想要别的名字，
  在**仓库设置**里改默认分支（已有仓库我们一律不动），或直接用已有分支的仓库上车
- **「已有仓库的默认分支是 master，会被改成 main 吗」** → 不会。只要远端已有任何分支，
  两个阶段都直接跳过，只打一条日志

### 别让脚本凭空造出一个 main（实测踩到的第二个坑）

「跟随参考上游项目」定了默认分支是 `master`，但如果同步脚本自己又推了个 `main`，
仓库里就会多出一个谁也没要的分支 —— 空仓库时它甚至可能成为**仓库的默认分支**。

根因：下发脚本 `sync-upstream-target.sh` 里 `TARGET_BRANCH` 默认成 `main`，
`git push origin HEAD:main` 就凭空造出了 `main`。

现在改成**不传 `TARGET_BRANCH` 就只在本地提交、不推送**，绝不猜分支名。
两条既有链路恰好都满足这个前提：

- 流水线：模板里设了 `SYNC_NO_PUSH=1`，推送与开 PR 交给后续阶段
- 同步官初装：在引导分支 `sync/bootstrap` 上跑，随后自己推该分支

所以调用脚本时**不要**给 `TARGET_BRANCH` 传值；确实要塞到某个分支时才显式传。
- **「为什么没有参考项目的提交历史」** → 铺源/快照式只落一个提交，不复刻参考项目历史。
  要的就是"内容同步过来"，历史不影响使用；正常增量同步（已有共同祖先）才会保留参考项目历史
- **「只改频率也要重新跑一次同步吗」** → 不用。改 `.cnb/git-sync.yml` 的 `crontab` 就够，
  定时任务会按新频率跑；想立刻同步一次就去流水线页面手动触发
